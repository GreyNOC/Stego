# Security Policy

## Supported versions

GreyNOC Stego Studio receives security fixes on the **latest tagged release** only. Older releases are not patched.

| Version  | Supported |
| -------- | --------- |
| `v1.x`   | Yes       |
| `< v1.0` | No        |

## Reporting a vulnerability

**Do not open a public GitHub issue for a security vulnerability.**

Please use one of the following private channels:

1. **Preferred** — GitHub Security Advisories: open a private advisory at  
   <https://github.com/GreyNOC/Stego/security/advisories/new>
2. Alternatively, contact the maintainers directly via the email listed on the
   GitHub profile at <https://github.com/GreyNOC>.

Please include:

- A description of the issue and the security impact (confidentiality / integrity / availability).
- The repository commit hash or release tag affected.
- Minimal reproduction steps using **synthetic test data** — see the section below.
- Your assessment of severity and any suggested mitigation.

We will acknowledge reports within 5 business days and aim to provide a fix or
status update within 30 days. Coordinated disclosure timelines can be agreed on
a case-by-case basis.

## Do not include secrets in reports

When reporting an issue, please do not include:

- Real passwords or passphrases (use a throw-away password such as `test-1234`).
- Real plaintext payloads or decrypted hex output that contain personal data.
- Carrier files that contain real secrets — instead, reproduce against a fresh
  image (e.g., a PNG generated by the test suite's `make_source_image` helper)
  and a non-sensitive payload.
- `stego_debug.log` contents from a production machine. If you need to attach a
  log, regenerate it in a clean environment with `GREYNOC_DEBUG=1` and a
  synthetic password and payload.

If a report inadvertently includes a real secret, treat that secret as
compromised: rotate / retire it and redo any operations that relied on it.

## Scope

In scope:

- Steganography injection and extraction code paths (`stego_core.py`, `stego_carriers.py`, `stego_hex_tool.py`).
- The Tkinter desktop app (`greynoc_stego_extractor_app.pyw`).
- The CLI and POSIX launcher (`greynoc_stego_cli.py`, `greynoc-stego`).
- The PyInstaller spec and the Android build script with respect to bundling
  vulnerable dependencies or shipping secrets.
- GitHub Actions workflows and Dependabot configuration.

Out of scope:

- Vulnerabilities that require the attacker to already control the user's
  desktop session (e.g., reading the clipboard after a legitimate decrypt).
- Side-channel attacks that require physical access or root on the host.
- Issues caused by third-party tools (Expo, EAS, OpenCV) outside of how this
  project invokes them.

## Cryptographic notes

The crypto primitives in this project are intentionally simple:

- **Cipher:** AES-256-GCM (`Crypto.Cipher.AES.MODE_GCM`) — authenticated encryption.
- **KDF:** PBKDF2-HMAC-SHA256, 200,000 iterations, 16-byte random salt per payload.
- **Nonce:** 12 random bytes per payload via `Crypto.Random.get_random_bytes`.
- **Authentication:** the GCM tag is verified before any plaintext is returned;
  a tampered ciphertext or wrong password fails with
  `Password is wrong or payload was modified.`

If you discover a way to recover plaintext without the correct password, to
forge a payload that passes GCM verification, or to cause the application to
return plaintext before the tag check, that is in scope and high severity.
Please report it through the channels above.
